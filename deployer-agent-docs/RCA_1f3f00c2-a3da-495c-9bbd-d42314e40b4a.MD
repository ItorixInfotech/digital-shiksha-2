# RCA — College Predictor paid unlock fails after a real Razorpay payment

**Site:** https://www.digitalshiksha.in  (deployment `digital-shiksha-2`, active run `1f3f00c2-a3da-495c-9bbd-d42314e40b4a`)
**Symptom:** Student pays on the Razorpay Payment Page, is redirected to `/predictor?paid=1`, then `POST /api/predictor/unlock` returns **404** "No new ₹X payment found from this mobile number yet…".

## Evidence (production logs, 2026-10-26 07:13–07:16 UTC, run 1f3f00c2)

Every failed unlock emitted the same diagnostic line:
```
lib.razorpay - INFO - Razorpay find_by_phone: scanned=4 phone_match=0 fee_match_unused=0 phone_amounts=[] statuses=[] fee=59900
INFO: POST /api/predictor/unlock HTTP/1.1 404 Not Found
```
and the underlying Razorpay call succeeded:
```
httpx - INFO - HTTP Request: GET https://api.razorpay.com/v1/payments?from=...&count=100&skip=0 "HTTP/1.1 200 OK"
```

### What each field means here
- **scanned = 4** — the account/mode that the production RAZORPAY_KEY_ID/SECRET belongs to contains only **4 payments total** in the last 48h.
- **phone_match = 0, phone_amounts = [], statuses = []** — NOT ONE of those 4 payments carries the student's mobile (in `contact` or in page-form `notes`). The student's payment is simply **not present in the account this key reads.**
- **fee = 59900** paise = ₹599 → the exam being unlocked is **MHT CET Pharmacy**.

### Key authenticates — it is not an auth/credential error
`GET /v1/payments` returns **200 OK** (not 401/403). `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` are both set (non-empty) on the active run. So the key is valid; it just points at the wrong account/mode.

### razorpay_payment_id was NOT passed on the redirect
Across all attempts the code path taken was `find_by_phone` (the **list** endpoint `GET /v1/payments?from=...`). There is **no** `GET /v1/payments/pay_xxx` single-payment lookup anywhere in the logs — which is the branch (`fetch_payment`) that runs only when `razorpay_payment_id` is present. Conclusion: the Razorpay Payment Page redirect to `/predictor?paid=1` did **not** include `razorpay_payment_id`, so the backend always falls back to scanning payments by phone.

## Root cause

The production `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` belong to a **different Razorpay account, or a different mode (likely test-mode), than the account that owns the live Payment Pages** (`rzp.io/rzp/6vvZNmq` for Pharmacy, and the other `pl_...` pages the app reads). When a student pays, the payment is created in the **page-owner's** account. `find_by_phone` lists `/v1/payments` for the **key's** account, which contains only 4 unrelated payments and never the student's — so phone match = 0 → 404.

(I cannot read the secret value — it is encrypted — so I cannot confirm from here whether it is `rzp_test_…` vs `rzp_live_…` or which account it belongs to. The user must verify this in the Razorpay Dashboard. The behavior — valid key, authenticates, but the paid transaction is absent from its payment list — is conclusive that it is the wrong account/mode.)

## Not the cause (ruled out)
- **Phone format mismatch (+91 / 12-digit / missing):** cannot be the cause. `_phones()` already normalizes any contact to the last 10 digits and also scans page-form `notes`, so a `+91`/12-digit contact would still match. More decisively, `phone_amounts=[]`/`statuses=[]` mean there was **no payment record with that phone to inspect at all** — the payment isn't in this account.
- **Amount/fee mismatch:** irrelevant — no phone-matched payment existed to even check the amount (`fee_match_unused=0` follows from `phone_match=0`).
- **App health / deploy pipeline:** app is healthy; `/v1/payments` returns 200. This is a runtime-config (secret) problem, not a code crash or a build/deploy failure.

## Fixes

1. **User (Secrets) — resolving fix.** In Deployment Panel → Secrets, set `RAZORPAY_KEY_ID` and `RAZORPAY_KEY_SECRET` to a **LIVE** API key pair (`rzp_live_…`) generated from the **same Razorpay account that owns the Payment Pages** (the account where `rzp.io/rzp/…` links and the students' payments actually land). Redeploy. Then re-test a real payment.
2. **User / Third-party (verify in Razorpay Dashboard).** Confirm (a) the account is in **Live** mode, (b) that account's Payments list shows the student's ₹599 payment, and (c) the API key was generated under that same account. The 4-payment account the current key reads is the wrong one.
3. **Code (E1) — robustness, secondary.** The unlock depends entirely on phone-scanning `/v1/payments` (48h window, contact must be on the payment) because the Payment Page redirect does not pass `razorpay_payment_id`. Even with the correct key this is fragile. Recommend either configuring the Payment Pages to append `razorpay_payment_id` on redirect (then the reliable `fetch_payment` branch is used) and/or recording payments via a Razorpay **webhook** keyed to the page/account. This is an improvement, not the proximate cause.

# RCA — digitalshiksha.in: raw HTML shows home `<title>`/meta on every route (SEO)

## Scope
Debug/report only. Nothing was changed. Deployment `digital-shiksha-2`, active run `fa9f6c9c-6731-4b58-b040-d1e370382131`, template `farm_ts_react_mongo_base_image`, **frontend_type = kubernetes** (nginx serves static files inside the pod and proxies `/api` to FastAPI). **No manifest overrides exist** — the deploy uses the stock FARM template manifests (confirmed: `get_deployment_manifest` returned `not_found` for nginx.conf / Dockerfile / config.yaml / build-frontend-artifacts.sh).

## Root cause (confirmed)
Production serves a **single static `index.html` for every non-`/api` route** via nginx SPA fallback. That `index.html` carries the hard-coded home `<title>`/`<meta description>` baked at build time (`frontend/index.html`). Per-page titles/descriptions are injected **client-side by JS at runtime only** — there is **no SSR and no prerender** in the repo (`grep` for prerender/ssr/react-snap/puppeteer/vite-plugin-ssr → none). Raw-HTML consumers (view-source, SEO crawlers that don't execute JS) therefore always see the home meta.

Confirmed live: `GET https://digital-shiksha-2.emergent.host/colleges/iit-bombay` → 200, `content_type text/html`, body is `index.html` with `<title>Digital Shiksha | Colleges, Courses, Exams & Admission Counselling in India</title>` and the home description.

## Answers to the three questions

### 1) How frontend routes are served in production (static server / SPA fallback / try_files)
- Served by **nginx inside the k8s pod**, root `/usr/share/nginx/html` (the Vite `dist/` output, copied in by the Dockerfile as `build/`).
- Exact rule (stock FARM `nginx.conf`):
  ```nginx
  location / {
    root /usr/share/nginx/html;
    index index.html index.htm;
    try_files $uri /index.html;
  }
  ```
- **try_files order = `$uri` then `/index.html`.** It tries the request path as an exact physical file; if that file does not exist it serves `/index.html` (SPA fallback). 
- **Nested prerendered files are effectively NOT served for extensionless SPA routes.** There is **no `$uri/` entry** in try_files, so nginx does NOT do directory-index resolution. Consequences:
  - `/colleges/iit-bombay` → tries a literal file named `colleges/iit-bombay` (none) → falls straight to `/index.html`. A `dist/colleges/iit-bombay/index.html` would **NOT** be picked up (that needs `try_files $uri $uri/ /index.html`).
  - `dist/colleges/iit-bombay.html` would **NOT** match `/colleges/iit-bombay` either (no `.html` is appended).
  - Only an **exactly-matching** physical path is served, e.g. a request to `/colleges/iit-bombay.html` would serve that file if it existed.
- Configurable from repo? Only via a **deploy-manifest override of `nginx.conf`** (not a plain app-source file). None exists today.

### 2) Is backend/Mongo/env reachable during the production frontend build? Post-build hook?
- The frontend build runs in an **isolated Docker/Cloud-Build `frontend-build` stage**. Only `frontend/` is copied in. **The backend is not running and MongoDB is NOT reachable; no app secrets/custom env are injected.** The only build-time inputs are build ARGs: `BACKEND_URL` (prod backend URL, sed-substituted into `frontend/.env` → `REACT_APP_BACKEND_URL`), `PREVIEW_DOMAIN`, and optional Artifact-Registry tokens. No `MONGO_URL`, no `DB_NAME`, no custom secrets.
- So a DB-driven build-time prerender (enumerate college/course slugs from Mongo → emit per-page HTML) is **not possible from the DB** in this pipeline. The Cloud Build stage does have outbound network, so a build script could in principle fetch the public `/api/sitemap.xml` from the already-live prod backend to get the slug list — but that is not wired today.
- Post-build hook: the stock Dockerfile does `yarn install && yarn build`, then renames `dist`→`build`, then the final backend stage. There is a `POST_INSTALL_COMMANDS` ARG but it runs in the **backend final stage** (after pip install), not as a frontend post-build hook. The repo-controllable place to emit extra files into `dist` is a **Vite plugin `closeBundle`/`writeBundle` hook** in `vite.config.ts` — but it still has no DB/secret access at build time. `build-frontend-artifacts.sh` exists but is for **cloudflare-frontend apps only**; this app is kubernetes-frontend so it is unused.

### 3) How `/sitemap.xml` and `/robots.txt` are routed in production; can non-`/api` HTML routes hit the backend?
- **In production they are NOT routed to the backend.** They are served as **static files by nginx**, because `frontend/public/sitemap.xml` and `frontend/public/robots.txt` ship in the build. Confirmed live:
  - `GET /sitemap.xml` → 200, `text/xml` = the **static sitemap-index** that merely points to `https://www.digitalshiksha.in/api/sitemap.xml`.
  - `GET /robots.txt` → 200, `text/plain` = the **static robots** file.
- The backend's dynamic SEO endpoints are at **`/api/sitemap.xml`** and **`/api/robots.txt`** — the `seo.router` is mounted under `api_router = APIRouter(prefix="/api")` in `backend/server.py`. There is **no backend route at the site root** `/sitemap.xml` or `/robots.txt`.
- Why preview looked like "the backend serves them": `frontend/vite.config.ts` defines a **dev/preview-only proxy** (`server.proxy` and `preview.proxy`) that rewrites root `/sitemap.xml`→`/api/sitemap.xml` and `/robots.txt`→`/api/robots.txt`. **That proxy is Vite-dev-server only and does NOT exist in production nginx.**
- Can other non-`/api` HTML routes be routed to the backend (so FastAPI returns `index.html` with per-page `<title>`/`<meta>` injected)? **Not today.** Stock nginx proxies only `location /api`; `location /` is static with SPA fallback. HTML page routes never reach FastAPI. Enabling that requires an **nginx.conf manifest override** (e.g. a named `@backend` fallback: `try_files $uri @backend;` + `location @backend { proxy_pass http://127.0.0.1:8001; }`) plus a backend catch-all route that renders `index.html` with injected meta. That is a deploy-manifest change, not a plain repo edit.
- Note: the deployment has `crawler_enabled: true` at the platform level. I could not inspect what that edge behavior does from here; it did not alter the raw-HTML responses observed above (per-page route still returned home meta).

## Recommended fixes (not applied)
Any of these is viable; (A) is the smallest.
- **(A) Build-time prerender/meta injection (Code, E1).** Add a Vite `closeBundle` step (or a post-`vite build` script) that, for each route, writes a physical `dist/<route>.html` (or `dist/<route>/index.html`) containing the correct `<title>`/`<meta>`. Route list can come from a static manifest or fetched from the live `/api/sitemap.xml` at build time (DB is not reachable; the API is). **This alone is not enough** — because current nginx `try_files` has no `$uri/`, it won't serve nested prerendered files; so pair it with an nginx override that resolves directory indexes or matches the emitted file names.
- **(B) Serve HTML routes from the backend (Code + nginx override).** Override `nginx.conf` to fall non-`/api` requests through to FastAPI (`try_files $uri @backend`), and have the backend return `index.html` with per-request `<title>`/`<meta>` injected (it can read Mongo at runtime, so meta can be fully dynamic). Heavier but fully dynamic.
- Either path needs an **nginx.conf manifest override**, which currently does not exist and would be authored on the deploy side, not in plain app source.

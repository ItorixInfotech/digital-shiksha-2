## Question 2: Intermittent 520 / 20s hangs on GET /api/redirects and /api/seo/pages
These are NOT an enquiries bug and NOT a persistent outage. They are a single-worker concurrency/boot problem on tier_0. Backend runs **one uvicorn worker** (`--workers 1`, `--reload` stripped by entrypoint; from the read-only supervisor template) on a 250m CPU (¼ core) limit.

Two confirmed code patterns overload that single worker/event loop:

### 2a. Boot-time event-loop blocking (explains "right after the latest deploy")
`server.py` lifespan spawns many `asyncio.create_task(...)` jobs that do heavy CPU-bound work on the SAME event loop: `load_cap_data()` (~29k MHT CET CAP rows, gzip+JSON), `load_kcet_data()` (~1.6k), `load_comedk_data()` (~800), `run_college_import()/run_college_enrich()`, plus one-time seeding. Synchronous CPU work inside an async task blocks the loop, so requests arriving during the post-boot seeding window stall → Cloudflare 520 / long hangs. Pods show 0 restarts, so this is confined to each deploy's boot window (~07:30–07:32 after this run) — matching your "especially right after the latest deploy."

### 2b. Per-request external fan-out to Razorpay (explains anytime cache-miss slowness)
`GET /api/predictor/exams` (routers/predictor.py:97-98) builds its response with `await razorpay.exam_fee(e.name)` **sequentially for up to 8 paid exams**. `exam_fee` (lib/razorpay.py:31-50) does an httpx GET to the static Razorpay Payment Page (`rzp.io` → 302 → `pages.razorpay.com`), `follow_redirects=True`, `timeout=8`, cached only 10 min (`_FEE_TTL=600`).
Confirmed in live logs: at 08:25:52–08:26:02 (pod 6ktnf) and 08:28:09–08:28:19 (pod mt7wg), one `/api/predictor/exams` triggered a cascade of ~14 sequential `rzp.io`/`pages.razorpay.com` calls (~0.7s each ≈ 8–10s). On a single worker a cache-miss request occupies request capacity for ~6s normally and up to ~64s worst case if Razorpay is slow, starving concurrent requests during a page load → intermittent slow/520 on sibling calls like /redirects and /seo/pages.

### 2c. Transient Mongo/Atlas latency — INFERRED, not reproduced
The isolated 20s `/api/seo/pages` hang while `/api/health` stayed fast (0.15s) points to an occasional stall in a Mongo-touching path (pool contention from boot seeding writes, or an Atlas-side blip), because `/health` never touches Mongo. At inspection Atlas was healthy (instant queries, lead wrote at 08:35:59), so no persistent fault. Minor contributor: the `settings` collection read by `/seo/pages` (`find_one({"key": KEY})`) has only the default `_id_` index (no index on `key`) — negligible at its tiny size but worth adding. This item is inferred; I could not reproduce it (sandbox has no live DB/secrets or boot-timing).

## Recommended fixes
**Code (E1, requires redeploy) — primary:**
1. Deploy the already-built invalid-email fix for POST /api/enquiries (treat blank email as None before validation / loosen EmailStr handling + fix the toast). This is the real "form not working" cause.
2. Stop the boot tasks from blocking the event loop: run the CPU-bound parse/seed work off-loop (`asyncio.to_thread` / `run_in_executor`) or move one-time seeding into a migration/one-shot job, so request serving isn't stalled during post-deploy boot.
3. Harden the Razorpay fan-out on the hot path: fetch the ≤8 pages concurrently (`asyncio.gather`) with a short timeout and/or warm `_FEE_CACHE` from a background task, and serve the `PAID_EXAMS` fallback immediately rather than blocking `/api/predictor/exams` on live Razorpay reads.
4. (Minor) add an index on `settings.key`.

**Config (User, Resources tab) — optional resilience, NOT a proven single cause:** tier_0's 250m CPU + single worker is what makes 2a/2b user-visible; there was no OOMKill or confirmed CPU-throttle-at-limit tied to the failures (0 restarts). Raising the tier adds headroom but the correct fix is the code changes above — more CPU only masks the blocking.

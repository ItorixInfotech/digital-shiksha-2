# RCA — "after payment Predictor PDF not shown" (digitalshikshaonline.com / digital-shiksha-2)

## Status vs previous RCA
The earlier RCA blamed missing `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` on a deploy (run `1449aee0`, 06:26) that predated the 06:39 secret save. **That is now resolved:**
- Two deploys ran AFTER the secret save: run `101eac1e` (completed 07:47) and the current active run `5d8218ad` (completed 08:10).
- `list_secrets` on the active run shows `RAZORPAY_KEY_ID` = present/non-empty and `RAZORPAY_KEY_SECRET` = present/non-empty.
- `GET /api/predictor/exams` returns 200 with `payment_auto_check:true` for both paid exams (MHT CET ₹1500, MHT CET Pharmacy ₹599).
- Proof that the keys actually authenticate against Razorpay: run `101eac1e` logs show `GET https://api.razorpay.com/v1/payments?from=... → 200 OK` on every unlock attempt.

So the secrets problem is fixed. The PDF still doesn't appear for a **different** reason.

## Exact failing step
`POST /api/predictor/unlock` → **HTTP 404** ("No new ₹X payment found from this mobile number yet…").
Evidence — run `101eac1e` (active 07:47–08:10) logs, 3 attempts:
- 08:07:40 — Razorpay `GET /v1/payments` 200 → `POST /api/predictor/unlock 404`
- 08:09:14 — Razorpay `GET /v1/payments` 200 → `POST /api/predictor/unlock 404`
- 08:09:38 — Razorpay `GET /v1/payments` 200 → `POST /api/predictor/unlock 404`

Because unlock 404s, no `predictor_unlocks` doc is ever written → no `receipt_id` → the `pdf_url` / "Download PDF" step the frontend performs never has anything to serve. `predictor_unlocks` collection = **count 0** (db `digital-shiksha-2-app`), confirming no paid unlock has ever succeeded in production. (`predictions` = 13, all from the free exams.)

## Where the 404 comes from (code, backend/lib/razorpay.py → find_by_phone)
Flow (confirmed in source): student pays on the rzp.io payment page, enters their mobile, clicks "I've paid". Frontend (`PredictorPayment.tsx`) sends `{prediction, name, phone:<clean 10 digits>, payment_id:""}`. Backend takes the `else` branch and calls `find_by_phone(phone, used, fee)`:
```
r = GET https://api.razorpay.com/v1/payments?from=now-86400&count=100   # auth = RAZORPAY_KEY_ID/SECRET
mine = [p for p in r.items
        if (p.contact or "").replace(" ","")[-10:] == phone
        and p.amount == fee and p.id not in used]
if not mine: raise 404 "No new ₹{fee} payment found…"
```
A 404 means: among the payments these API keys returned for the last 24h, **none** had (last-10-digits of contact == submitted mobile) AND (amount == exact fee in paise) AND (unused).

## What is ruled OUT
- **Submitted phone format** — NOT the cause. Frontend normalizes to exactly 10 digits (`replace(/\D/g,"").slice(-10)`, validated `/^[6-9]\d{9}$/`) before sending; backend normalizes the Razorpay `contact` to its last 10 digits too. Standard `+91XXXXXXXXXX` contacts match fine.
- **Secrets missing/blank** — NOT the cause anymore (both keys present; Razorpay API returns 200).
- **Backend crash / 5xx / ReportLab PDF build error** — none seen; the failure is a clean 404 before any PDF/doc work.
- **Data being purged** — no TTL index on `predictor_unlocks`; redeploys don't wipe data. The collection is empty because unlock has never succeeded, not because docs were deleted.

## Most likely root cause (needs owner verification — not reproducible from here)
The Razorpay keys authenticate (200) but the **student's actual payment is not present in / not matchable within the list those keys return**. Ranked candidates:
1. **Account / mode mismatch (leading):** the `RAZORPAY_KEY_ID`/`SECRET` in Secrets belong to a *different Razorpay account or mode* than the one that owns the rzp.io payment pages (`rzp.io/rzp/6wXdLUk`, `rzp.io/rzp/6vvZNmq`) the students actually pay on — including the classic **test-mode key vs live payments** case (`rzp_test_…` would return 200 but only test payments). `GET /v1/payments` would then never contain the student's payment → 404. (Note: the deployer's `matches_expected` check is a full-string compare, so it could NOT confirm the `rzp_live_` prefix — the key's mode/account must be verified in the dashboard.)
2. **Amount mismatch:** the captured payment's `amount` (paise) is not exactly `150000` / `59900` (e.g. payment page allowed a different/custom amount, or a fee was added) → filtered out.
3. **Contact missing/different:** the payment's `contact` on Razorpay is empty (some UPI flows) or the student paid with a different mobile than they typed → no match.
4. **Outside window / pagination:** payment older than 24h, or >100 payments in 24h pushing it past `count=100` (no pagination in code).

## Recommended fixes
1. **User / Third-party (Razorpay dashboard) — primary:** In the Razorpay dashboard that owns the two rzp.io payment pages, confirm (a) you are in **Live** mode, (b) the API key in Deployment → Secrets (`RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`) is a **live key of that same account**, and (c) a recent test payment on the page actually appears under Payments with `status=captured`, the expected `amount` (₹1500→150000 / ₹599→59900 paise), and a `contact` holding the payer's mobile. Correct the key in Secrets if it is from a different account/mode and redeploy. Do one end-to-end test payment and confirm `predictor_unlocks` gets a doc.
2. **Code (optional hardening, E1):** `find_by_phone` currently gives no diagnostic on the 404 — it can't be told apart from "wrong amount" vs "empty list" vs "contact mismatch" in logs. Add a log of `len(items)` and, per candidate, the reason it was filtered (amount vs contact vs used). Consider widening the window beyond 24h and adding pagination if volume can exceed 100/day. These improve diagnosis/robustness but are NOT the root cause.

## Minor anomaly (non-blocking)

With no TTL and no data wipe on redeploy, this was most likely a proxy/CDN-cached PDF response rather than a live DB-backed unlock. Not related to the current 404 and not worth chasing unless it recurs.

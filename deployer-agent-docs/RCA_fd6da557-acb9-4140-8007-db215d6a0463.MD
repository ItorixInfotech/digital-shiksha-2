# RCA — Lead alert email "not received" on live (digitalshiksha.in)

## Problem statement
User reports lead-alert email (triggered by POST /api/enquiries → BackgroundTask `notify_new_lead`) is not received in production, while it works in preview. Emergent email API returns 202 for a manual test.

## Which build is live
Active run **fd6da557-acb9-4140-8007-db215d6a0463** (redeploy, success, completed 2026-10-27 08:48 UTC). Source inspected in an eph sandbox: `backend/lib/email.py` contains the **retry-on-429/5xx loop** (`for attempt in range(3)` with backoff) and the lenient email handling. **The latest code is live** — this is not a stale-build problem.

## Evidence (all from the active run)
1. **Secrets (list_secrets with equals):**
   - `LEAD_ALERT_EMAIL` → is_empty=false, **matches_expected=true** for `enquiry@digitalshiksha.in` (the owner inbox per memory/SPEC.md and preview .env — not empty, not the `delivered@resend.dev` test address used in tests).
   - `EMERGENT_EMAIL_KEY` → is_empty=false, **matches_expected=true** (same `ek_1839...` key as preview; valid).
   - `EMAIL_BASE_URL` — **not a secret by design**: it is a hardcoded constant in `lib/email.py` (`https://integrations.emergentagent.com`). The live request went to the correct URL, so nothing is missing.
2. **Pod logs (run fd6da557):**
   - `POST /api/enquiries HTTP/1.1 201 Created`
   - `lib.email - INFO - Lead alert for 033786af-f390-4b94-9e5f-8b8421d7d27f sent: 01a17c8c-f512-7b25-a2ac-944de24a4851`
   - `httpx - HTTP Request: POST https://integrations.emergentagent.com/api/v1/email/send "HTTP/1.1 202 Accepted"`
   - No "alert skipped", no 4xx/429/5xx from the email API, no missing-key/KeyError, no exception after the POST.
   - (Unrelated: `lib.whatsapp ERROR ... 400: WhatsApp requires an approved message template (ContentSid)` — WhatsApp alerts are off because the Twilio template SIDs are empty; this does not affect email.)

## Root cause
The production email pipeline is **working correctly**. The lead alert is generated, sent, and **accepted by the Emergent email API with HTTP 202 and a message id (`01a17c8c-f512-7b25-a2ac-944de24a4851`)**, addressed to the correct owner inbox `enquiry@digitalshiksha.in`. The alert is not being skipped by the dedup rule and no error is logged. Per the reporter's own criterion (3), a 202 + id means the failure is **downstream of our system — delivery to the recipient mailbox** (spam/junk filtering, mailbox routing/MX, or domain SPF/DKIM for mail from Emergent-managed Resend to a custom-domain inbox).

## Secondary caveat (dedup)
`routers/public.py` line ~195–210: a submission from the **same phone within 10 minutes** is saved but intentionally sends **no second alert**. If the user tested repeatedly with the same number, only the first submission per 10-minute window emails. This can look like "some leads didn't email" but is by design.

## Fixes
- **User (test_and_verify / deliverability):** Check the `enquiry@digitalshiksha.in` mailbox's **Spam/Junk** folder and confirm the mailbox exists and receives external mail (MX/forwarding). If mail is being filtered, whitelist the Emergent/Resend sender and ensure the digitalshiksha.in domain's SPF/DKIM permit the sending service. Verify against message id `01a17c8c-f512-7b25-a2ac-944de24a4851`, which our side confirms was accepted.
- When testing, use a **different phone number** (or wait >10 min) so the dedup rule does not suppress the alert.

## No code, secret, or infra change required on the deployment
Secrets are correct, the live build is current, and the API accepted the message.

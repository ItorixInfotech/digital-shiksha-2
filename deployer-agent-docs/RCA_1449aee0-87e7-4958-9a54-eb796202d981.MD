# RCA — Razorpay not working on /predictor (Digital Shiksha, custom domain)

## Problem statement
Razorpay payment verification on the `/predictor` tab does not work on the live site
(`digitalshikshaonline.com`). Students pay on the static Razorpay page, click "I've paid"
(POST `/api/predictor/unlock`), but the unlock/verify flow fails. Reported "after website live on domain."

## Root cause (PROVEN)
The live Razorpay keys are **not present in the running production pod's environment**.

- The active/serving run is `1449aee0-87e7-4958-9a54-eb796202d981`, created 2026-10-24 **06:25:11**,
  completed **06:26:06**.
- The live Razorpay key slot was saved in the Secrets tab at **06:39** — i.e. AFTER the last deploy finished.
- No deploy has run since (this is the newest run in history).
- Secrets are only injected into the pod during the `write_secrets` step of a deploy. Since no deploy
  ran after 06:39, the pod still runs with the pre-06:39 environment.
- `list_secrets` on the active run (metadata_available=true, authoritative) returns **no `RAZORPAY_KEY_ID`
  and no `RAZORPAY_KEY_SECRET` at all**.

Consequence: in production `payment_auto_check = bool(RAZORPAY_KEY_ID and RAZORPAY_KEY_SECRET)` = **False**.
The Razorpay REST verification call in `backend/lib/razorpay.py` has no credentials to authenticate with,
so the unlock flow cannot match any payment. This fully explains the symptom.

## Failing step
Not a pipeline step — all recent runs succeeded. The failure is a **stale production environment**: a
Secrets-tab edit (06:39) that was never carried into a deploy. Serving run env lacks the Razorpay keys.

## Corroborating evidence (alternate theories ruled out)
- **/api routing on the app:** `GET /api/predictor/exams` on the live URL → 200 with real JSON. `/api` is
  correctly proxied to the FastAPI backend.
- **Cookie / custom-domain routing:** frontend_type = kubernetes. The custom domain is a Cloudflare custom
  hostname pointing to the same pod; the in-pod nginx serves the frontend and proxies `/api` on the SAME
  origin. The `ds_unlocks` cookie (httpOnly, Secure, path `/api/predictor`, SameSite=Lax) is therefore
  first-party on the custom domain and is set/sent normally. NOT a cookie or `/api`-routing problem.
- **Logs (last 24h):** zero `POST /api/predictor/unlock` entries; only `/health`, one `/api/config` 404,
  and a `cap-meta` 200. No 401/404/502 from Razorpay — because the backend never calls Razorpay (no keys).
  Consistent with the flow being disabled client-side by `payment_auto_check:false`.
- **PUBLIC_SITE_URL:** present and non-empty in the active run (email PDF links are fine).
- **Domains:** `digitalshikshaonline.com` verified, SSL active, DNS linked — healthy.
  `www.digitalshikshaonline.com` NOT verified, SSL `pending_validation` — a separate, cosmetic issue,
  unrelated to Razorpay.

## Fix (user action)
1. In Deployment Panel → Secrets, confirm `RAZORPAY_KEY_ID` (should start with `rzp_live_`, not
   `rzp_test_`) and `RAZORPAY_KEY_SECRET` are set to the LIVE values.
2. **Redeploy** the app. Only a new deploy runs `write_secrets` and injects the keys into the pod.
   After redeploy, verify `GET /api/predictor/exams` shows `payment_auto_check: true`, then re-test the
   "I've paid" flow with a real live payment.
3. (Optional, unrelated) Fix `www.digitalshikshaonline.com` DNS/SSL if the www host is needed.

## Verification note
Root cause proven via deploy timeline + `list_secrets` (keys absent from serving run). NOT reproduced in an
eph pod — this is an environment/secret state issue (live keys + live Razorpay data), which a sandbox
without secrets cannot reproduce.
